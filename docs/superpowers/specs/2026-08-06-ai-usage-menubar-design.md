# AI Usage — menu bar app (บัญชี × provider)

วันที่: 2026-08-06 · สถานะ: ออกแบบเสร็จ รอทำแผนลงมือ

## เป้าหมาย

แสดงโควตา AI ทุกเจ้าที่ใช้จริงบนเครื่องนี้ใน macOS menu bar โดยแยกตาม **บัญชี × provider**
ไม่ใช่แค่บัญชี และไม่แสดงตัวเลขที่วัดไม่ได้จริง

## ทำไมไม่ใช้ OpenUsage

OpenUsage เป็นแอป native Swift ฟรีที่ทำงานนี้อยู่แล้ว เหตุผลที่ยังสร้างเอง (จากที่ผู้ใช้เลือก):

1. **หลายบัญชี ccs** — เครื่องนี้มี 4 บัญชี (default / mooz / spark / work) สลับด้วย `ccs sw`
   OpenUsage ออกแบบมาให้ดูบัญชีเดียว
2. **provider ที่ OpenUsage ไม่มีหรือทำไม่ดี** — Qwen, GLM, DeepSeek, Kimi
3. **ควบคุม design เอง**

## การค้นพบสำคัญ: หน่วยนับไม่ตรงกัน

**นี่คือข้อมูลที่แพงที่สุดในเอกสารนี้ — อย่าลืม**

| Provider | หน่วยที่ผู้ให้บริการใช้นับ | ประกาศตัวเลขไหม | เราคำนวณ % ได้ไหม |
|---|---|---|---|
| **Claude (Anthropic)** | "usage per session" (สื่อนอกรายงานเป็น **ชั่วโมง**) | **ไม่** — บอกแค่ Max 5x = "5 เท่าของ Pro" | **ไม่ได้จากตัวเลขประกาศ** — ได้เฉพาะปรับเทียบจากที่เคยชนเอง |
| **Codex (OpenAI)** | **จำนวนข้อความ** ต่อ 5 ชม. + weekly | ไม่ครบ | **ได้** — มันเขียน % มาให้ใน log |
| **GLM (Zhipu)** | **จำนวน prompt** | **ใช่** — Lite/Pro/Max ≈ 80/400/1,600 ต่อ 5 ชม. | **ได้** ถ้ารู้ tier |
| **Qwen Cloud (Alibaba, ต่อกับ cc)** | **ไม่รู้หน่วย** — วัดแล้วไม่ใช่ทั้ง request และ token | **ใช่** — 3,000 ต่อ 5 ชม. / 10,000 ต่อ 7 วัน | **ได้ ถ้าหา API ของ dashboard เจอ** |
| **Qwen Code CLI (OAuth)** | ขึ้นกับแผน (ดูล่าง) | บางส่วน | **ขึ้นกับแผน** |

### สรุปที่ต้องจำ

ปัญหาของ Claude **ไม่ใช่** "ไม่รู้ตัวเลขเพดาน" แต่คือ **หน่วยมันคนละอย่าง** —
Anthropic ไม่ได้นับเป็น token ต่อให้รู้เพดานก็แปลงจาก token ไม่ได้
ทุกความพยายามที่จะโชว์ `token / เพดาน × 100` สำหรับ Claude คือการเดา

Claude มี weekly limit **2 อัน** (รวมทุกโมเดล + เฉพาะ Sonnet) ไม่ประกาศตัวเลขทั้งคู่
และ 5-hour limit ถูกขยายเป็น 2 เท่าเมื่อ 6 พ.ค. 2026

### GLM — ตัวเดียวที่วิจัยแล้วใช้ได้ทันที

- Lite/Pro/Max ≈ **80 / 400 / 1,600 prompt ต่อ 5 ชม.** + weekly cap
- **GLM-5.2 กิน 3 เท่าช่วง peak (14:00–18:00 UTC+8) / 2 เท่านอก peak**
- หน้าต่าง 5 ชม. รีเซ็ต 5 ชม.หลังเริ่มใช้โควตา · weekly เริ่มนับจากวันสมัคร
- **นับ prompt ได้จาก transcript** (นับ turn ของผู้ใช้ ไม่ใช่ token) → **ได้ % จริงโดยไม่ต้องรอชนลิมิต** ถ้ารู้ tier
  ⚠️ เอนจินตอนนี้นับแต่ token **ยังไม่มีตัวนับ prompt** — เป็นงานใหม่ที่ต้องเขียน

### Qwen Cloud (ต่อกับ Claude Code) — มีเพดานประกาศจริง

ยืนยันจาก `~/.ccs/qwenc.settings.json`:

```
ANTHROPIC_BASE_URL           https://token-plan.ap-southeast-1.maas.aliyuncs.com/apps/anthropic
ANTHROPIC_MODEL              qwen3.8-max
ANTHROPIC_DEFAULT_SONNET_MODEL   deepseek-v4-flash-0731   ← สำคัญ
ANTHROPIC_DEFAULT_HAIKU_MODEL    deepseek-v4-flash-0731
```

หน้า dashboard (Individual Plan · Standard) ประกาศตัวเลขตรงๆ:

| หน้าต่าง | เพดาน | ที่เห็นตอนถ่าย |
|---|---|---|
| 5 ชั่วโมง | **3,000** | เหลือ 100% (ยังไม่เริ่ม) |
| 7 วัน | **10,000** | เหลือ 47.9% · รีเซ็ต 2026-08-12 20:03 |

**แต่ยังไม่รู้ว่า 3,000 นับเป็นหน่วยอะไร** — วัดแล้วไม่ตรงกับสมมติฐานไหนเลย:
ในหน้าต่าง 7 วันปัจจุบันมี **1,205 request** (deepseek-flash 1,114 + qwen3.8-max 91)
แต่ dashboard บอกใช้ไป ~5,210 หน่วย → **ไม่ใช่ 1 request = 1 หน่วย** (ต่างกัน ~4.3 เท่า)
token รวม 229M ก็ไม่ลงตัวกับ 5,210 เช่นกัน

> **อย่าเดาหน่วย** dashboard นี้ต้องดึงตัวเลขมาจาก API สักตัว
> ถ้าหา endpoint นั้นเจอ = ได้ระดับ "วัดได้จริง" เลย ไม่ต้อง reverse-engineer
> **ต้องถามผู้ใช้ว่า dashboard นี้อยู่ URL ไหน**

### Qwen มี 3 ตัวที่ชื่อซ้ำกัน อย่าปนกัน

| แหล่ง | โมเดล | ใครคิดเงิน | แสดงยังไง |
|---|---|---|---|
| ccs `qwenc` | `qwen3.8-max` + `deepseek-v4-flash-0731` | **Alibaba** (token-plan MaaS) | แถบ % จากเพดาน 3,000/10,000 |
| ccs `spark` | `qwen36-35b-code` / `-fast` | **ไม่มีใคร** — `http://192.168.1.67:4000` ในบ้าน | ไม่ต้องมีแถบโควตา |
| qwen-code CLI | `~/.qwen/oauth_creds.json` | Alibaba (คนละแผน) | แถวแยก |

**Alibaba ปิด free OAuth tier ไปแล้ว 15 เม.ย. 2026** (เดิม 2,000 req/วัน + 60/นาที)
สำหรับ qwen-code CLI ตัวที่สาม ถ้าอยู่แผนจ่ายตาม token ต้อง**แสดงเงิน ไม่ใช่ %**
เพราะไม่มีเพดานให้ชน แถบ % จะโกหก — โหมดนี้ยังไม่มีในดีไซน์

## จะเอาตัวเลขจริงมาจากไหน

### ✅ Claude — แก้จบแล้ว: `cachedUsageUtilization` ใน `~/.claude.json`

**ไม่ต้องปรับเทียบ ไม่ต้องแปลง token ไม่ต้องยิง API ไม่ต้องมี proxy**
Anthropic ส่ง % ทางการมาให้ตรงๆ แล้ว Claude Code เก็บลงไฟล์ไว้เอง

```json
"cachedUsageUtilization": {
  "fetchedAtMs": 1786084686283,
  "utilization": {
    "five_hour": { "utilization": 5,  "resets_at": "2026-08-07T07:10:00Z" },
    "seven_day": { "utilization": 96, "resets_at": "2026-08-08T20:00:00Z" },
    "limits": [
      { "kind": "session",       "percent": 5,   "severity": "normal",   "is_active": false },
      { "kind": "weekly_all",    "percent": 96,  "severity": "critical", "is_active": false },
      { "kind": "weekly_scoped", "percent": 100, "severity": "critical", "is_active": true,
        "scope": { "model": { "display_name": "Fable" } } }
    ]
  }
}
```

**ยืนยันงานวิจัยก่อนหน้าทุกข้อ** — weekly มี 2 อันจริง (`weekly_all` + `weekly_scoped` ต่อโมเดล)
และ `weekly_scoped: Fable = 100% · is_active: true` คือคำอธิบายของข้อความ
`You've reached your Fable 5 limit` ที่เจอ 5 ครั้งในบท "ตัวกรอง"

#### สิ่งที่ตายไปพร้อมกับการค้นพบนี้

| ของที่ออกแบบ/เขียนไว้ | สถานะ |
|---|---|
| `calibrate_budget5h()` + `quota_hit_events()` | **ไม่ต้องใช้กับ Claude แล้ว** — เก็บไว้ใช้กับ GLM/Qwen ที่ยังไม่มีทางอื่น |
| `budget5h` / `budgetWeek` ใน config | **ไม่ต้องให้ผู้ใช้กรอกอีกต่อไป** |
| แผน % 3 ระดับ (ดิบ → เทียบตัวเอง → ปรับเทียบ) | **ยกเลิกสำหรับ Claude** — ข้ามไประดับ "วัดได้จริง" เลย |
| สถานะ "ประมาณ" (แถบลาย + `~`) ของ Claude | **ไม่ใช้แล้ว** — Claude เป็นแถบทึบเหมือน Codex |

#### ของแถมที่ได้มาฟรี

- `severity: normal | critical` → **ระบบแจ้งเตือนใกล้ชนลิมิตไม่ต้องคิดเกณฑ์เอง** ใช้ของ Anthropic
- `is_active` → บอกว่าตอนนี้ตัวไหนกำลังบล็อกอยู่จริง
- `scope.model.display_name` → บอกว่าเป็นลิมิตของโมเดลไหน
- `resets_at` → เวลาสัมบูรณ์ ตรงกับที่ออกแบบให้ Swift นับถอยหลังเอง

#### แคชนี้ refresh เฉพาะบัญชีที่กำลังใช้ — วัดแล้ว

อ่านคีย์นี้จาก config ของทั้ง 4 บัญชี (2026-08-07 06:40 UTC):

| บัญชี | 5h | 7d | อายุ `fetchedAtMs` | tier |
|---|---|---|---|---|
| default | 5% | 96% | **7 นาที** | Max 20x · Fable ชน 100% (`is_active`) |
| mooz | 0% | 27% | **2,434 นาที ≈ 40 ชม.** | Max 5x |
| spark | — | — | — | **ไม่มีคีย์เลย** |
| work | — | — | — | **ไม่มีคีย์** · `default_raven` (Team) |

**ข้อสรุปสามข้อ:**

1. **แคชไม่ refresh เอง** — `mooz` เก่า 40 ชม. คือหลักฐาน มัน refresh ตอนบัญชีนั้นถูกใช้เท่านั้น
   เราสั่งให้ refresh ไม่ได้ (ต้องรัน Claude Code ในบัญชีนั้น)
2. **`spark` ไม่มีคีย์เพราะไม่เคยคุยกับ Anthropic** — ชี้ไป `192.168.1.67:4000`
   ยืนยันโมเดล "ถัง = endpoint" อีกชั้น
3. **`work` (Team) ไม่มีคีย์** — ยังไม่รู้ว่าเพราะไม่ได้ใช้นาน หรือ Team ไม่ได้รับข้อมูลนี้
   → ต้องเช็คซ้ำหลังใช้บัญชีนั้น

#### ผลต่อดีไซน์: สองสัญญาณ คนละคำถาม

วัดต่ออีก 30 ตัวอย่าง 29 นาที ระหว่างใช้ Claude Code หนักตลอด: **`fetchedAtMs` ไม่ขยับเลย**
ข้อมูลแก่จาก 3 นาทีเป็น 32 นาทีระหว่างที่ทุกอย่างทำงานถูกต้อง

**ดังนั้นอายุเป็นสัญญาณที่ผิดสำหรับข้อมูลนี้** — ตัวเลขอายุ 40 ชม. ที่ไม่มีใครใช้ต่อ = ถูกเป๊ะ
ส่วนตัวเลขอายุ 5 นาทีที่ยิงไป 200 request หลังจากนั้น = ผิดไปแล้ว

| สัญญาณ | มาจาก | ตอบคำถาม | คุมอะไร |
|---|---|---|---|
| **Freshness** | `generated` — เราสแกนเมื่อไหร่ | engine ยังทำงานอยู่ไหม | แถบเตือน · สถานะตาย · ตัว `↻` |
| **Certainty** | `confidence` — fetchedAt + traffic | ตัวเลขนี้ถูกไหม | หน้าตาของแถบและตัวเลข |

`generated` อัปเดตทุก 60 วิจริง เกณฑ์ 3/30 นาทีจึงถูกต้องสำหรับมัน
แต่คุณภาพของตัวเลขต้องใช้ `window_confidence` ไม่ใช่อายุ

| confidence | ความหมาย | แสดงเป็น |
|---|---|---|
| `valid` | ถูกต้อง ณ ตอนนี้ | แถบทึบ · `5%` |
| `zero` | หน้าต่างรีเซ็ตแล้วและเงียบสนิท | แถบว่าง · `0%` |
| `lower_bound` | มี traffic หลังแคช ของจริงสูงกว่านี้ | แถบทึบถึงค่าที่รู้ + ส่วนที่เหลือเป็นลาย · **`≥5%`** |
| `unsure` | หน้าต่างใหม่และมี traffic ไม่รู้เลย | แถบจุดประ · `—` |

**`lower_bound` คือสถานะปกติระหว่างทำงาน** ไม่ใช่กรณีขอบ — ตลอด 29 นาทีที่วัดมาจะเป็นสถานะนี้
`≥5%` ซื่อสัตย์และใช้งานได้จริง ต่างจาก "ตาย" ซึ่งผิด

#### transcript ยังมีประโยชน์ — แต่คนละหน้าที่กับที่คิดไว้

เดิมจะใช้ transcript **คำนวณ %** (ซึ่งทำไม่ได้ เพราะหน่วยไม่ตรง)
หน้าที่จริงของมันคือ **บอกว่าตัวเลขที่แคชไว้ยังใช้ได้อยู่ไหม**

| เงื่อนไข | สรุปได้ว่า |
|---|---|
| ไม่มี traffic เลยหลัง `fetchedAtMs` และแคชเก่ากว่า 5 ชม. | **บล็อก 5 ชม. รีเซ็ตไปแล้วแน่นอน → 0% (มั่นใจได้)** |
| ไม่มี traffic หลัง `fetchedAtMs` แต่ยังไม่ถึง 5 ชม. | ตัวเลขเดิมยังใช้ได้ |
| มี traffic หลัง `fetchedAtMs` | ตัวเลขเดิมเป็น**ขอบล่าง** — ของจริงสูงกว่านี้ |

สองแหล่งเสริมกันพอดี: `cachedUsageUtilization` บอกความจริง ณ เวลา T ·
transcript บอกว่ามีอะไรเกิดขึ้นหลัง T ไหม
กรณี `mooz` (เงียบมา 40 ชม.) จึงพูดได้เต็มปากว่า 5 ชม. = 0% ไม่ใช่ "ไม่รู้"

### ที่ค้นแล้วไม่มี — อย่าเสียเวลาซ้ำ (ก่อนเจอ `cachedUsageUtilization`)

| ที่ค้น | ผล |
|---|---|
| transcript JSONL (104 ไฟล์ 5 วันล่าสุด · ค้น 11 คำ: `ratelimit` `quota` `remaining` `unified` …) | **ไม่มีฟิลด์เกี่ยวกับลิมิตเลยสักตัว** |
| `~/.claude/stats-cache.json` | มีแต่ยอด token ต่อโมเดล · ค้างตั้งแต่ 2026-05-12 · **ไม่มีเพดาน** |
| `~/.claude/` ทั้งโฟลเดอร์ (ค้นชื่อไฟล์ usage/limit/quota/subscription) | ไม่มีไฟล์ไหนตรงเลย |
| `~/.ccs/logs/current.jsonl` | บันทึกแค่ event ตอนเรียก CLI ไม่มี HTTP response |

**สรุป: Claude Code ไม่เก็บสถานะโควตาลงดิสก์** ต่างจาก Codex ที่เขียน `rate_limits`
ลง rollout log (ซึ่งเป็นเหตุผลเดียวที่ Codex ให้ % จริงได้ตั้งแต่แรก)

### มันอยู่ที่เดียว: response header ของ HTTP

ทุก endpoint ที่พูดโปรโตคอล Anthropic ส่ง header กลุ่ม `anthropic-ratelimit-*` กลับมาทุก request
**ตัวเลขที่เราต้องการวิ่งผ่านเครื่องนี้ตลอดเวลา แต่ไม่มีใครเก็บไว้**

#### GLM — ยิง endpoint จริงแล้ว ไม่มี coding plan

`GET https://api.z.ai/api/monitor/usage/quota/limit` (endpoint มีจริง มีเครื่องมืออื่นใช้อยู่)
ยิงด้วย token จาก `~/.ccs/glm.settings.json` ได้:

```json
{ "code": 500, "msg": "当前用户不存在coding plan", "success": false }
```

**บัญชีนี้เป็นแบบจ่ายตามใช้ (wallet) ไม่ใช่ subscription** → ไม่มีโควตา 5 ชม./weekly ให้แสดง
ตัวเลข 80/400/1,600 prompt ที่วิจัยไว้**ใช้กับบัญชีนี้ไม่ได้**

แต่เจอ `[1308][Usage limit reached for 5 hour]` 6 ครั้งช่วง 11–23 ก.ค. → **น่าจะเคยมีแผนแล้วหมดอายุ**
ถ้าผู้ใช้ต่ออายุเมื่อไหร่ endpoint นี้จะคืนโควตาจริงทันที **โค้ดต้องรองรับทั้งสองแบบ**

#### Qwen Cloud — รู้หน่วยแล้ว แต่คำนวณเองไม่ได้

หน่วยคือ **Credits** (ไม่ใช่ request ไม่ใช่ token) และ 3,000/10,000 ตรงกับแผน **Standard** พอดี

| แผน | 5 ชม. | 7 วัน |
|---|---|---|
| Lite | 700 | 2,500 |
| **Standard** ← ของผู้ใช้ | **3,000** | **10,000** |
| Pro | 12,000 | 40,000 |

**แต่ Alibaba ไม่ประกาศสูตรแปลง token → credit** และไม่มี API สาธารณะให้ถามยอดคงเหลือ
(ที่วัดได้: 1,205 request ≈ 5,210 credits — ไม่ใช่อัตราคงที่ต่อ request แน่นอน)
→ **ต้องได้ URL/endpoint ของหน้า dashboard ถึงจะแสดง % ได้** ไม่งั้นแสดงได้แค่เวลารีเซ็ตจาก 429

#### `cachedUsageUtilization` ไม่ refresh ระหว่างเซสชัน — วัดแล้ว

เก็บตัวอย่างทุก 60 วิ ระหว่างใช้งาน Claude Code หนักต่อเนื่อง: **`fetchedAtMs` ไม่ขยับเลยสักครั้ง**
รวมกับ `mooz` ที่เก่า 40 ชม. สรุปว่า refresh เฉพาะตอน**เปิด `/usage`** หรือ**เริ่มเซสชันใหม่**
เราสั่ง refresh เองไม่ได้ → **ต้องโชว์อายุ ไม่ใช่แกล้งทำเป็นสด**

### โหมด "แสดงเงิน" ไม่ใช่ของเสริมอีกต่อไป

เดิมคิดว่าเป็นกรณีขอบของ qwen-code CLI ตอนนี้ **GLM ต้องใช้แน่นอน**
ถังที่ไม่มีเพดานต้องแสดงคนละแบบ: ไม่มีแถบ % · แสดงยอดใช้เป็นเงิน + แนวโน้ม
แถบ % ที่ไม่มีเพดานจริงคือการโกหกที่ดูน่าเชื่อที่สุดในแอปนี้

## หน่วยข้อมูล: (บัญชี × provider)

**ไม่ใช่บัญชี** เพราะบัญชีเดียวยิงได้หลาย provider และโควตาถูกบังคับแยกกันคนละที่

หลักฐานจากเครื่องนี้ (3 สัปดาห์):

| บัญชี | โมเดลที่เรียกจริง |
|---|---|
| default | **3 ถังปนกันในโฟลเดอร์เดียว** — Anthropic (opus-4-8 11,477 · fable-5 10,109 · opus-5 1,576 · sonnet-5 300) · z.ai (glm-5.2 2,858) · Qwen Cloud (deepseek-v4-flash 1,114 + qwen3.8-max 91) |
| mooz | Claude ล้วน |
| **spark** | **qwen36-35b ล้วน — ไม่มี Claude เลย** ทั้งที่ oauth บอก "Max 20x" |
| work | Claude ล้วน |

`spark` เป็นหลักฐานว่าทำไมเชื่อ oauth อย่างเดียวไม่ได้ — ป้าย plan จะโกหก

**สาเหตุที่ `default` ปนกัน:** `qwenc.settings.json` กับ `glm.settings.json` **ไม่ได้ตั้ง `CLAUDE_CONFIG_DIR`**
(ต่างจาก `spark.settings.json` ที่ตั้ง) ccs จึงสลับแค่ endpoint แต่เขียน transcript ลง `~/.claude` เหมือนเดิม
→ โฟลเดอร์เดียวมี 3 ถังโควตาปนกัน **แยกด้วยชื่อบัญชีไม่ได้เลย**

### ถังโควตา = endpoint ไม่ใช่ยี่ห้อโมเดล

**นี่คือสิ่งที่สเปกฉบับแรกทำผิด** เดิมเขียนไว้ว่าให้แยก provider จากชื่อโมเดล:

```python
REGISTRY = [("claude-","Claude"), ("glm","GLM"), ("qwen","Qwen"), ("deepseek","DeepSeek"), ...]
```

**ใช้ไม่ได้** เพราะ `~/.ccs/*.settings.json` พิสูจน์ว่า:

- `deepseek-v4-flash-0731` (1,114 ครั้ง) **ไม่ใช่บัญชี DeepSeek** — มันคือช่อง Sonnet
  ของแผน Qwen Cloud → กินโควตา 3,000/10,000 ของ Qwen Cloud
  กฎ prefix จะแยกมันไปเป็นถังของตัวเอง = **นับโควตาหายไป 92%**
- `qwen36-35b` (spark, ฟรี) กับ `qwen3.8-max` (Alibaba, มีเพดาน) ขึ้นต้น `qwen` เหมือนกัน
  กฎ prefix จะรวมสองอันนี้เป็นถังเดียว = **เอาของฟรีไปปนกับของที่มีเพดาน**

**ชื่อโมเดลบอกได้แค่ว่าจะวาดโลโก้อะไร · `ANTHROPIC_BASE_URL` ต่างหากที่บอกว่าโควตาไปลงถังไหน**

### สร้างแผนที่จาก config ของผู้ใช้เอง

transcript **ไม่ได้บันทึก base URL ไว้** (ตรวจแล้ว — ไม่มีฟิลด์นั้น)
แต่ `~/.ccs/*.settings.json` มีครบ: 1 ไฟล์ = 1 endpoint + 4 ช่องโมเดล
อ่านไฟล์พวกนี้แล้วสร้าง `model → ถัง` เอง ไม่ต้อง hardcode:

| ไฟล์ | endpoint | ครอบคลุมโมเดล |
|---|---|---|
| `qwenc.settings.json` | `token-plan.…maas.aliyuncs.com` | qwen3.8-max, deepseek-v4-flash-0731 |
| `glm.settings.json` | `api.z.ai/api/anthropic` | glm-5.2, glm-5.2[1m], glm-4.7 |
| `spark.settings.json` | `192.168.1.67:4000` (LAN) | qwen36-35b-code, qwen36-35b-fast |
| *(ไม่มีไฟล์)* | `api.anthropic.com` | `claude-*` |

เพิ่ม provider ใหม่ = ผู้ใช้เพิ่ม settings ให้ ccs ตามปกติ **แอปรู้เอง**
โมเดลที่ไม่อยู่ในไฟล์ไหนเลยตกถัง **"ยังไม่รู้จัก"** ไม่ถูกทิ้งเงียบ

> ⚠️ ห้ามอ่านค่า `ANTHROPIC_AUTH_TOKEN` ในไฟล์พวกนี้ อ่านแค่ `ANTHROPIC_BASE_URL` กับช่องโมเดล

### ความสดของข้อมูล — ตัวเลขค้างอันตรายกว่าไม่มีตัวเลข

launchd อาจตายเงียบ (python พัง · path เปลี่ยน · permission หลุด) แล้วแอปจะอ่านไฟล์เดิม
**โชว์ "เหลือ 47%" อย่างมั่นใจทั้งที่ข้อมูลค้างมา 6 ชั่วโมง** — ผิดหลัก "ไม่แกล้งทำเป็นรู้" ที่ตกลงกันไว้

`snapshot.json` มีฟิลด์ `generated` อยู่แล้ว ใช้คำนวณอายุได้เลย

| สถานะ | อายุ | แถบ menu bar | popover |
|---|---|---|---|
| **สด** | ≤ 3 นาที | `◐ 47% 2h14m` | ปกติ |
| **ค้าง** | 3–30 นาที | `◐ 47% ↻18m` + หรี่ทั้งชิ้น | แถบบางบนสุด "อัปเดตล่าสุด 18 นาทีที่แล้ว · [ตรวจใหม่]" |
| **ตาย** | > 30 นาที · อ่านไฟล์ไม่ได้ | `◐ — ↻2h` **ไม่มีตัวเลข** | แถบเข้มขึ้น + บรรทัดสุดท้ายของ `/tmp/aiusage.err.log` + ปุ่ม [ซ่อมให้] |

**ทำไมเอาอายุไปแทนที่ช่องนับถอยหลัง** — ตอนข้อมูลค้าง คำถามที่ผู้ใช้ต้องการคำตอบคือ
"ตัวเลขนี้เก่าแค่ไหน" ไม่ใช่ "อีกนานแค่ไหนรีเซ็ต" · เวลารีเซ็ตยังดูได้ใน popover
และเปลี่ยนรูปร่างชัด (`2h14m` → `↻18m`) ไม่ใช่แค่หรี่สี — ผ่านกฎ `color-not-only`

**ที่ตายต้องไม่โชว์แถบทึบ** ให้ทุกแถบตกไปเป็นพื้นผิว "ไม่รู้" (จุดประ) และซ่อนตัวเลข
แถบทึบที่ 47% จากข้อมูลเมื่อ 2 ชม.ที่แล้วคือการโกหก ไม่ใช่การประมาณ

**ปุ่ม [ซ่อมให้]** = `launchctl kickstart -k gui/$UID/com.aiusage.snapshot`

#### แต่เป้าหมายคือแทบไม่ต้องใช้สถานะ "ตาย" เลย

สถานะตายคือทางออกสุดท้ายที่ซื่อสัตย์ ไม่ใช่สิ่งที่ควรได้เห็นบ่อย
ตรวจโค้ดจริงแล้ว **สองในสามชั้นป้องกันมีอยู่แล้ว**:

| ความเสี่ยง | สถานะจริงในโค้ด |
|---|---|
| ไฟล์เขียนค้างกลางทาง → JSON พัง | ✅ กันแล้ว — `write_json()` เขียน `.tmp` แล้ว `os.replace()` (atomic) |
| บัญชีเดียวพัง → ทั้ง snapshot พัง | ✅ กันแล้ว — `collect()` มี `try/except` ต่อบัญชี |
| บัญชีที่พัง**หายไปเงียบๆ** | ❌ **ยังไม่กัน** — `except Exception: continue` |

**ช่องโหว่จริงคือข้อสาม และมันแย่กว่าสถานะตาย** เพราะบัญชีที่พังจะ*หายไปจากรายการ*
ผู้ใช้เห็น 3 แถวแทนที่จะเป็น 4 แล้วไม่รู้เลยว่าขาดไป — เป็นความล้มเหลวที่มองไม่เห็น
ต่างจากสถานะตายที่อย่างน้อยก็ประกาศตัว

### ลำดับการแก้ เรียงตามผลที่ได้ต่อความพยายาม

**1 · เปลี่ยน `continue` เป็นแถวที่บอกว่าพัง** — เปลี่ยนไม่กี่บรรทัด ได้ผลมากสุด

```python
except Exception as e:                     # เดิม: continue
    items.append({"group": "Claude Code", "label": acc["label"],
                  "error": str(e)[:120], "pct": None})
```

สถานะ "ตาย" กลายเป็น**ต่อแถว** ไม่ใช่ทั้งแอป และบอกชื่อบัญชีกับสาเหตุตรงๆ
บัญชีอื่นยังแสดงตัวเลขจริงต่อไป

**2 · เลิกใช้ launchd — ให้แอปเรียก Python เอง** ← เปลี่ยนโครงสร้าง ได้เยอะสุด

ตอนนี้ launchd เป็นชิ้นส่วนที่พังได้โดยที่แอปไม่มีทางรู้สาเหตุ ต้องเดาจากอายุไฟล์
ถ้าแอปเรียก `Process` เองบน `Timer` ทุก 60 วิ:

- **ลบ plist ออกจากรายการสิ่งที่พังได้ทั้งชั้น** — ไม่มี bootstrap ไม่มี path ให้ผิด
- แอปได้ **exit code + stderr ทันที** → บอกสาเหตุจริงได้เลย ไม่ต้องอนุมานจาก `generated`
- แอปไม่รัน = ไม่มีไอคอนบน menu bar = **เห็นชัดในตัวเอง** ไม่ใช่การโกหกเงียบ
- `setup.sh` สั้นลง ตัดขั้นตอนที่พังบ่อยที่สุดทิ้ง

*แลกกับ:* ไม่อัปเดตตอนแอปปิด — ซึ่งไม่เป็นไร เพราะตอนนั้นไม่มีใครดูอยู่แล้ว

**3 · ห้ามเขียนทับด้วยผลลัพธ์ว่าง** — ถ้ารอบนี้ได้ 0 แถวแต่ของเดิมมี ให้เก็บของเดิมไว้
(atomic write กันไฟล์พังแล้ว แต่ไม่ได้กันการเขียนทับด้วยข้อมูลว่างที่ "สำเร็จ")

**4 · ตัดจบที่ 45 วินาที** — `Process` ต้องมี timeout ไม่งั้นสแกนที่ค้างจะกินรอบถัดไปเรื่อยๆ
และห้ามเริ่มรอบใหม่ขณะรอบเก่ายังไม่จบ

#### สองอย่างที่ต้องระวัง ไม่งั้นผู้ใช้จะเรียนรู้ที่จะเมิน

1. **เครื่อง sleep** — ปิดฝาข้ามคืน ตื่นมา snapshot อายุ 8 ชม. แต่จะถูกต้องเองใน 60 วิ
   ถ้าไม่กันไว้ ผู้ใช้จะเจอสถานะ "ตาย" ทุกเช้า แล้วเลิกเชื่อสถานะนี้ไปเลย
   → ฟัง `NSWorkspace.didWakeNotification` แล้ว**ผ่อนผัน 90 วินาที** นับเป็นสดไว้ก่อน
2. **นับถอยหลังไม่ควรค้างตาม** — คำนวณจาก timestamp สัมบูรณ์ (`block.end`) ในไฟล์
   ฝั่ง Swift ลบเวลาปัจจุบันเอง ไม่ต้องรอ Python → **เวลารีเซ็ตแม่นเสมอแม้ข้อมูลค้าง**
   มีแค่ตัวเลข token/% เท่านั้นที่เก่า

### หน้า settings

ทุกแถวบอก **provider · บัญชี** + path เสมอ ตั้งเพดานผิดตัวไม่ได้
ช่องเพดานแยก 3 แบบชัด: *ยังไม่ได้ตั้ง* (จาง เอียง) / `4,800,000` (ทึบ = ใส่เอง) / `~62,000,000` (มี ~ = ระบบเดา)

## แผน % 3 ระดับสำหรับ Claude

เนื่องจากแปลง token เป็น % ไม่ได้ ให้ไต่ตามข้อมูลที่มีจริง:

1. **วันแรก** — token ดิบ + เวลา reset
2. **พอมีประวัติ** — เทียบกับ**สถิติของตัวเอง**
   "บล็อกนี้หนัก 80% ของบล็อกที่หนักที่สุดที่เคยใช้"
   ไม่ต้องรู้เพดานของ Anthropic เลย และบอกอะไรได้จริง ← **ยังไม่ได้ทำ**
3. **พอเคยชนลิมิตจริง** — % จากการปรับเทียบ ← **เขียนแล้วใน `ai-usage.60s.py`**

### กลไกปรับเทียบ (ทำแล้ว)

หา event ที่ `error == "rate_limit"` และ `apiErrorIsTransient is False`
แล้วย้อนหา token ณ เวลานั้น → median = `budget5hAuto`

**กรองออก 2 แบบ:**
- proxy ท้องถิ่น — error code ในวงเล็บ (`[1308]`) หรือคำว่า resource package / recharge / token-plan
- ลิมิตเฉพาะโมเดล — มี `/usage-credits`, `switch models`, `/model`

#### ตัวกรองนี้ทิ้งของจริงไป 2 ใน 3 แบบ

ไล่ข้อความ 429 จริงย้อนหลัง 30 วัน แล้วเทียบกับตัวกรอง:

| ข้อความจริงที่เจอ | ตัวกรองทำอะไร | ถูกไหม |
|---|---|---|
| `Your token-plan 5-hour quota has been exhausted. The quota will reset at 08-05 18:03:00 UTC` (2 ครั้ง) | **ทิ้ง** เพราะเจอคำว่า `token-plan` | ❌ **ผิด** — นี่คือ Qwen Cloud ของจริง คำว่า token-plan คือ**ชื่อโฮสต์** ไม่ใช่คำโฆษณา |
| `[1308][Usage limit reached for 5 hour. Your limit will reset at 2026-07-23 17:25:53]` (6 ครั้ง) | **ทิ้ง** เพราะเจอ `[1308]` | ❌ **ผิด** — นี่คือ GLM ของจริง |
| `You've reached your Fable 5 limit. Run /usage-credits…` (5 ครั้ง) | ทิ้ง | ✅ ถูก — ลิมิตเฉพาะโมเดล ไม่ใช่ลิมิตบัญชี |
| `Server is temporarily limiting requests (not your usage limit)` (5 ครั้ง) | ทิ้ง | ✅ ถูก — ชั่วคราว |

**ผลคือตอนนี้ไม่มี event เหลือให้ปรับเทียบเลย** ตรงกับที่วัดได้ว่า `pct: null` ทุกบัญชี

#### ของแถมที่ดีกว่าการปรับเทียบ: ข้อความบอกเวลารีเซ็ตมาให้ตรงๆ

ทั้ง Qwen Cloud และ GLM เขียน **ขนาดหน้าต่าง + เวลารีเซ็ตที่แน่นอน** มาในข้อความ 429
(`5 hour` · `reset at 2026-07-23 17:25:53`) ไม่ต้องเดาจาก timestamp เลย

→ ควร**พาร์สเวลารีเซ็ตจากข้อความ** เป็นแหล่งความจริงหลัก
ส่วนการปรับเทียบ token เอาไว้ใช้กับเจ้าที่ไม่บอกอะไรมาเลย (Claude)

#### ข้อจำกัดที่วัดแล้ว — กลไกนี้ยังใช้งานไม่ได้จริง

รัน `--json` ตรวจเมื่อ 2026-08-06: **ทั้ง 4 บัญชีได้ `pct: null`, `pctEstimated: false`**
คือเขียนเสร็จแล้วแต่ยังไม่เคยให้ตัวเลขสักครั้ง เพราะ:

| ข้อจำกัด | ผลที่ตามมา |
|---|---|
| มองย้อนแค่ **7 วัน** (`WEEK_DAYS`) | ถ้าไม่ชนลิมิตในสัปดาห์นี้ = ไม่มีค่า และค่าที่เคยได้ก็หายไปเอง |
| ใช้เฉพาะ hit ที่ `window == "5h"` | **weekly ไม่เคยถูกปรับเทียบเลย** ทั้งที่ Claude มี weekly limit 2 อัน |
| median ยอมรับ **n = 1** | ชนครั้งเดียวก็ออกตัวเลขที่ดูน่าเชื่อ ทั้งที่เป็นจุดข้อมูลเดียว |
| ตัด sample ที่ต่ำกว่า 500k token | กัน rate limit ต่อนาที แต่ก็ตัดบล็อกที่ชนจริงตอนใช้น้อยทิ้งด้วย |

**ต้องแก้:** เก็บผลปรับเทียบลงไฟล์ให้อยู่ข้ามสัปดาห์ + แสดงจำนวน sample ใน settings
(`~62M จาก 1 ครั้ง` ต่างจาก `~62M จาก 9 ครั้ง` มาก)

**สรุป:** ระดับ 3 พึ่งไม่ได้ในทางปฏิบัติ → **ระดับ 2 (เทียบสถิติตัวเอง) คือตัวที่สำคัญจริง** ไม่ใช่ของแถม

### บั๊กใน `setup.sh` ปัจจุบัน — "เสร็จแล้ว" ทั้งที่ยังรันโค้ดเก่า

`setup.sh:36-38` ลบแล้ว copy แล้ว `open` **โดยไม่ปิดแอปเก่าก่อน**

```bash
rm -rf /Applications/AIUsage.app      # ลบ bundle ได้ แต่ process เดิมยังรันจาก inode เก่า
cp -R "$APP" /Applications/
open /Applications/AIUsage.app        # มี instance รันอยู่แล้ว → แค่ activate ตัวเก่า
```

ผลคือสคริปต์พิมพ์ "เสร็จแล้ว" แต่ผู้ใช้ยังใช้ไบนารีเก่าอยู่ **จนกว่าจะ quit เอง**
เป็นบั๊กที่มองไม่เห็น — และจะทำให้ debug รอบถัดไปเสียเวลามหาศาล

### ที่ต้องแก้

1. **ปิดแอปเก่าก่อนแตะ `/Applications`**
   `osascript -e 'quit app "AIUsage"'` → รอ ≤ 5 วิ → ถ้าไม่ยอมค่อย `pkill -f 'AIUsage.app/Contents/MacOS'`
2. **build ให้เสร็จก่อนลบของเดิมเสมอ** — ลำดับปัจจุบันถูกแล้ว (เช็ค `-d "$APP"` ก่อน `rm -rf`) **อย่าไปสลับ**
   ไม่งั้น build พังแล้วผู้ใช้เหลือเครื่องที่ไม่มีแอปเลย
3. **ตัดขั้นตอน launchd ออกทั้งหมด** — แอปเรียก Python เองแล้ว (ดู "ลำดับการแก้" ข้อ 2)
   `--uninstall` ยังต้อง `launchctl bootout` เผื่อเครื่องที่เคยติดตั้งแบบเก่าไว้
4. **เวอร์ชันจาก git** — `CURRENT_PROJECT_VERSION` = `git rev-list --count HEAD`,
   `MARKETING_VERSION` = `git describe --tags --always` (ตอนนี้ตายตัวที่ `1.0` / `1`)
   ถ้าไม่ใช่ repo ให้ fallback `dev` / `0`
5. **ยืนยันว่าติดตั้งสำเร็จจริง** — รอ `snapshot.json` มี `generated` ใหม่ภายใน 90 วิ
   ไม่งั้นพิมพ์ `tail /tmp/aiusage.err.log` แล้ว `exit 1` · ห้ามพิมพ์ "เสร็จแล้ว" ลอยๆ
6. **`--uninstall`** — bootout job, ลบ plist, ลบแอป, ถามก่อนลบ `~/Library/Application Support/AIUsage/`
7. **แก้ข้อความท้ายสคริปต์** — ยังบอกให้ไป "Edit Widgets → หา โควตา AI"
   ซึ่งเป็นคำสั่งของ WidgetKit ที่**เลิกใช้แล้วตามสเปกนี้**
8. **`setup.sh:11`** `cp -f ../ai-usage.60s.py … || cp -f ai-usage.60s.py …`
   เดา path จากที่รัน → ใช้ `$ROOT` ให้ชัด

### รู้แล้วว่าต้องทำ (ไม่ต้องรอคำตอบ)

0. **สร้างแผนที่ model → ถัง จาก `~/.ccs/*.settings.json`** ← ต้องทำก่อนเพื่อน
   ทุกอย่างที่เหลือผิดหมดถ้าถังผิด
4. **แยกถังในเอนจิน** — ทำ (บัญชี × endpoint) ให้เป็นจริง ← งานใหญ่สุด
5. **จัดโฟลเดอร์** ให้ `App/` `Shared/` `Widget/` `launchd/` ตรงกับ `project.yml` ← ไม่งั้น `setup.sh` พัง
6. **ระดับที่ 2 ของแผน %** (เทียบสถิติตัวเอง) — ตัวที่ให้คุณค่าจริง ไม่ใช่ของแถม
7. **เก็บผลปรับเทียบข้ามสัปดาห์** + โชว์จำนวน sample
8. **ปรับเทียบ weekly** ด้วย ไม่ใช่แค่ 5 ชม.
9. **ตัวนับ prompt** สำหรับ GLM (คนละอย่างกับตัวนับ token)

10b. **พาร์สเวลารีเซ็ตจากข้อความ 429** — แม่นกว่าเดาจาก timestamp
11. **เอาแถวตัวนับกรอกเองออก** (ChatGPT/Qwen/Antigravity ที่ `pct: 0.0`)
12. **แจ้งเตือนใกล้ชนลิมิต** — ยังไม่ออกแบบ (CLAUDE.md ระบุว่ายังไม่มี)
13. **สถานะความสดของข้อมูล** — สด/ค้าง/ตาย + ผ่อนผันหลังเครื่องตื่น (ออกแบบแล้ว)
14. **แก้ `setup.sh` 8 ข้อ** — โดยเฉพาะปิดแอปเก่าก่อน copy (ออกแบบแล้ว)
